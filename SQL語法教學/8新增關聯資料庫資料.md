# 進階-2｜關聯新增：順序錯一步就報錯

> 💻 DBeaver（資料庫：`cafe_lab`）｜ 📄 練習腳本：[`8新增關聯資料庫資料.sql`](./8新增關聯資料庫資料.sql) ｜ 🎯 學完你會：依序寫入有關聯的資料，並用交易確保全有或全無

## 🎬 情境

一位客人在台北信義店點了 2 杯拿鐵和 1 個可頌。這一件事要寫進好幾張表：

```mermaid
flowchart LR
    A["1. 門市、分類、會員<br>(主檔)"] --> B["2. 員工、商品"] --> C["3. 訂單主檔"] --> D["4. 訂單明細"]
```

而且**不能只成功一半**：訂單寫了但明細失敗，帳就錯了。所以要用交易包起來。

## 1. 順序錯了會怎樣

門市還不存在，就先新增員工：

```sql
INSERT INTO staff (name, store_id, title, hired_on, salary)
VALUES ('張志明', 1, '店長', '2021-03-01', 52000);
```

> 🛑 **資料庫回應**：`insert or update on table "staff" violates foreign key constraint "staff_store_id_fkey"`

## 2. 正確順序：用交易包起來

指定編號（1、101…）是為了讓範例好讀，下一節會說明它的副作用。整段選取後一起執行：

```sql
BEGIN;

-- 第一步：獨立的主檔
INSERT INTO stores (store_id, name, address, region, phone) VALUES
    (1, '台北信義店', '台北市信義區忠孝東路五段', '北部', '02-2720-1111'),
    (2, '台中逢甲店', '台中市西屯區逢甲路',       '中部', '04-2451-4444');

INSERT INTO categories (category_id, name) VALUES
    (1, '義式咖啡'),
    (2, '現烤點心');

INSERT INTO customers (customer_id, name, phone, gender, joined_on) VALUES
    (1, '曾怡君', '0973-000-001', '女', '2023-03-27');

-- 第二步：依賴主檔的資料
INSERT INTO staff (staff_id, name, store_id, title, hired_on, salary) VALUES
    (1, '張志明', 1, '店長', '2021-03-01', 52000),
    (2, '陳美玲', 1, '正職咖啡師', '2022-07-15', 38000);

INSERT INTO products (product_id, category_id, name, price, cost, launched_on) VALUES
    (101, 1, '經典拿鐵',     95, 35, '2023-01-01'),
    (102, 2, '法式經典可頌', 65, 25, '2023-01-01');

-- 第三步：訂單主檔
INSERT INTO orders (order_id, order_date, order_time, store_id, staff_id, customer_id, payment_method, status) VALUES
    (1001, '2024-03-01', '09:30', 1, 2, 1,    '信用卡', '已完成'),
    (1002, '2024-03-01', '10:15', 1, 2, NULL, '現金',   '已完成');  -- 散客

-- 第四步：訂單明細
INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES
    (1001, 101, 2, 95),  -- 拿鐵 2 杯
    (1001, 102, 1, 65),  -- 可頌 1 個
    (1002, 101, 1, 95);

COMMIT;
```

查查看成果：

```sql
SELECT
    o.order_id AS 訂單,
    COALESCE(c.name, '散客') AS 顧客,
    p.name AS 商品,
    i.quantity AS 數量,
    i.quantity * i.unit_price AS 小計
FROM order_items i
JOIN orders o ON i.order_id = o.order_id
JOIN products p ON i.product_id = p.product_id
LEFT JOIN customers c ON o.customer_id = c.customer_id
ORDER BY o.order_id, p.product_id;
```

**執行結果**

| 訂單 | 顧客 | 商品 | 數量 | 小計 |
|---:|---|---|---:|---:|
| 1001 | 曾怡君 | 經典拿鐵 | 2 | 190 |
| 1001 | 曾怡君 | 法式經典可頌 | 1 | 65 |
| 1002 | 散客 | 經典拿鐵 | 1 | 95 |

`COALESCE(a, b)` 的意思是「a 是空值就顯示 b」。會員用 `LEFT JOIN`，散客才不會消失。

## 3. 陷阱：手動指定編號後，自動編號會撞號

`SERIAL` 有自己的計數器。剛剛我們手動填了 1、2，它不知道，還是從 1 開始數：

```sql
INSERT INTO stores (name, address, region)
VALUES ('高雄巨蛋店', '高雄市左營區博愛二路', '南部');
```

> 🛑 **資料庫回應**：`duplicate key value violates unique constraint "stores_pkey"`

解法是把計數器撥到目前的最大值：

```sql
SELECT setval('stores_store_id_seq', (SELECT MAX(store_id) FROM stores));

INSERT INTO stores (name, address, region)
VALUES ('高雄巨蛋店', '高雄市左營區博愛二路', '南部')
RETURNING store_id, name;
```

**執行結果**

| store_id | name |
|---:|---|
| 3 | 高雄巨蛋店 |

> [!TIP]
> **實務建議**：平常別自己指定編號。匯入舊資料必須指定時，匯完記得 `setval`。

## 4. 更好的寫法：讓資料庫編號，再拿回來用

實際開單時，訂單編號是資料庫產生的。用 `RETURNING` 取得編號，再新增明細。Python App 也是這樣做：

```sql
SELECT setval('orders_order_id_seq', (SELECT MAX(order_id) FROM orders));

INSERT INTO orders (order_date, order_time, store_id, staff_id, payment_method, status)
VALUES ('2024-03-02', '11:00', 1, 2, 'LINE Pay', '已完成')
RETURNING order_id;
```

**執行結果**

| order_id |
|---:|
| 1003 |

拿到編號 `1003` 後，再寫明細：

```sql
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (1003, 102, 2, 65);
```

## 5. 交易的威力：全有或全無

第二句故意寫錯商品編號，第一句也不會留下來。請一句一句執行：

```sql
BEGIN;

INSERT INTO orders (order_date, order_time, store_id, staff_id, payment_method, status)
VALUES ('2024-03-03', '12:00', 1, 2, '現金', '已完成');
```

```sql
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (1004, 999, 1, 95);
```

> 🛑 **資料庫回應**：`insert or update on table "order_items" violates foreign key constraint "order_items_product_id_fkey"`

出錯後，交易已經失效，只能退回：

```sql
ROLLBACK;

SELECT COUNT(*) AS 訂單筆數 FROM orders;
```

**執行結果**

| 訂單筆數 |
|---:|
| 3 |

訂單沒有多一筆，資料完全沒被弄髒。

## ⚠️ 常見卡關

| 錯誤訊息 | 原因 | 怎麼解 |
|---|---|---|
| `violates foreign key constraint` | 父資料還沒建 | 依主檔 → 訂單 → 明細的順序 |
| `duplicate key value ... "stores_pkey"` | 手動編號後 SERIAL 撞號 | 用 `setval` 校正 |
| `current transaction is aborted` | 交易中已出錯 | 執行 `ROLLBACK;` |
| 另一邊查不到剛寫的資料 | 還沒 `COMMIT` | 補上 `COMMIT;` |

**第 2 題**：`DELETE FROM orders WHERE order_id = 2001;` 執行後，它的明細會怎樣？為什麼？

<details>
<summary>看答案</summary>

```sql
DELETE FROM orders WHERE order_id = 2001;
SELECT COUNT(*) AS 剩餘明細 FROM order_items WHERE order_id = 2001;
```

**執行結果**

| 剩餘明細 |
|---:|
| 0 |

明細會一起被刪除，因為 `order_items.order_id` 設了 `ON DELETE CASCADE`。

# 進階-10｜索引與效能：資料變多也不會卡

> 💻 DBeaver（新資料庫：`cafe_perf`）｜ 🎯 學完你會：看懂查詢是不是全表掃描，並判斷什麼時候該建索引

## 🎬 情境

暖光咖啡開了三年，訂單從幾百筆變成幾萬筆。王經理問：「怎麼查某一天的訂單越來越慢？」

Excel 超過幾萬列就開始卡頓。資料庫也可能變慢，但有一個專門的解法：**索引（INDEX）**。

索引就像書本最後的索引頁。想找「交易」這個詞，不用從第一頁翻到最後一頁，查索引頁就知道在第幾頁。

## 1. 準備一個資料量大的資料庫

> [!WARNING]
> **請不要在 `cafe_shop` 裡做這一課。** 灌入大量資料後，其他課的答案都會對不上，所以要另外開一個資料庫。

```sql
CREATE DATABASE cafe_perf;
```

切換到 `cafe_perf`，依序執行這兩個檔案：

1. [`cafe_shop.sql`](../範例資料庫/中文範例資料庫/cafe_shop.sql)：建立資料表和基本資料
2. [`generate_100k_orders.sql`](../範例資料庫/中文範例資料庫/generate_100k_orders.sql)：自動產生 5 萬筆訂單

確認筆數：

```sql
SELECT COUNT(*) AS 訂單筆數 FROM orders;
```

**執行結果**：`50490`

> [!NOTE]
> 訂單是隨機產生的，所以某一天的筆數和下面的執行時間，你的結果都會略有不同。重點是看**掃描方式**和**時間的差距**。

## 2. 查詢是怎麼跑的：EXPLAIN ANALYZE

在查詢前面加上 `EXPLAIN ANALYZE`，資料庫就會告訴你它是怎麼找資料的：

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE order_date = '2024-06-15';
```

**執行結果（節錄）**

```text
Seq Scan on orders  (actual time=0.038..1.231 rows=145 loops=1)
  Filter: (order_date = '2024-06-15'::date)
  Rows Removed by Filter: 50345
Execution Time: 1.235 ms
```

| 看到的字 | 白話 |
|---|---|
| `Seq Scan` | 全表掃描：一筆一筆從頭看到尾 |
| `rows=145` | 找到 145 筆 |
| `Rows Removed by Filter: 50345` | 看了 5 萬多筆，其中絕大多數都不是要的 |
| `Execution Time` | 實際花費的時間 |

為了找 145 筆，資料庫看完了全部 5 萬筆，就像把整份 Excel 從第一列看到最後一列。

## 3. 建立索引

```sql
CREATE INDEX idx_orders_order_date ON orders (order_date);
```

| 寫法 | 白話 |
|---|---|
| `idx_orders_order_date` | 索引的名字，習慣寫成 `idx_表名_欄位` |
| `ON orders (order_date)` | 替 `orders` 的 `order_date` 建索引 |

再查一次同一句：

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE order_date = '2024-06-15';
```

**執行結果（節錄）**

```text
Bitmap Heap Scan on orders  (actual time=0.009..0.024 rows=145 loops=1)
  ->  Bitmap Index Scan on idx_orders_order_date
Execution Time: 0.029 ms
```

| | 建索引前 | 建索引後 |
|---|---|---|
| 掃描方式 | `Seq Scan` 全表掃描 | `Bitmap Index Scan` 使用索引 |
| 執行時間 | 約 1.2 ms | 約 0.03 ms |

快了約 40 倍。現在只有 5 萬筆，人感覺不出差別；資料到幾百萬筆，就是幾秒和瞬間的差異。

> [!TIP]
> 看到 `Index Scan` 或 `Bitmap Index Scan`，都代表有用到索引。

## 4. 索引不是萬能的

### 欄位被函式包起來，索引就用不上

```sql
EXPLAIN
SELECT * FROM orders WHERE TO_CHAR(order_date, 'YYYY-MM-DD') = '2024-06-15';
```

**執行結果**：`Seq Scan on orders`

索引裡存的是 `order_date` 本身，不是轉換後的文字，所以用不上。查日期範圍請直接比較欄位：

```sql
EXPLAIN
SELECT * FROM orders WHERE order_date >= '2024-06-01' AND order_date < '2024-07-01';
```

**執行結果**：`Bitmap Index Scan on idx_orders_order_date`

### 要的資料太多時，資料庫會選擇全表掃描

```sql
EXPLAIN
SELECT * FROM orders WHERE order_date >= '2024-01-01';
```

**執行結果**：`Seq Scan on orders`

這個條件幾乎符合所有資料。要拿走整本書的內容，直接從頭讀反而最快，資料庫會自己判斷。

## 5. 索引的代價

索引不是建越多越好：

| 代價 | 說明 |
|---|---|
| 佔用空間 | 這個索引約 360 kB，資料表約 3856 kB |
| 寫入變慢 | 每次新增或修改資料，索引也要跟著更新 |

**什麼時候該建？**

| 適合 | 不必要 |
|---|---|
| 資料量大，而且常出現在 `WHERE`、`JOIN` 的欄位 | 只有幾百筆的小表 |
| 能篩掉大部分資料的欄位，例如日期、會員編號 | 只有幾種值的欄位，例如狀態 |

> [!NOTE]
> `PRIMARY KEY` 和 `UNIQUE` 會自動建立索引，不用自己建。

查看目前有哪些索引：

```sql
SELECT indexname AS 索引名稱
FROM pg_indexes
WHERE tablename = 'orders'
ORDER BY indexname;
```

**執行結果**

| 索引名稱 |
|---|
| idx_orders_order_date |
| orders_pkey |

`orders_pkey` 就是主鍵自動建立的索引。

不需要的索引可以刪除，資料不會受影響：

```sql
DROP INDEX idx_orders_order_date;
```

## ⚠️ 常見卡關

| 狀況 | 原因 | 怎麼解 |
|---|---|---|
| 建了索引，還是 `Seq Scan` | 資料量太少、符合的資料太多，或欄位被函式包住 | 這不一定是錯誤，資料庫會選它認為最快的方式 |
| `relation "idx_..." already exists` | 索引已經建過 | 換名字，或先 `DROP INDEX` |
| `orders` 只有 490 筆 | 沒有執行產生資料的腳本，或連錯資料庫 | 確認工具列是 `cafe_perf`，再執行腳本 |
| 第二次查詢的時間變短 | 資料已經在記憶體裡 | 正常現象，多跑幾次比較穩定的數字 |

## ✍️ 動手練

**第 1 題**：查某位會員的訂單時，先用 `EXPLAIN` 看掃描方式，再建立索引比較。

<details>
<summary>看答案</summary>

```sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 12;
-- 結果：Seq Scan on orders

CREATE INDEX idx_orders_customer_id ON orders (customer_id);

EXPLAIN SELECT * FROM orders WHERE customer_id = 12;
-- 結果：Bitmap Index Scan on idx_orders_customer_id
```

</details>

**第 2 題**：`status` 只有「已完成」和「已退款」兩種值，適合建索引嗎？

<details>
<summary>看答案</summary>

通常不適合。每個值都佔了很大比例，索引篩不掉多少資料，資料庫多半還是會全表掃描，索引反而佔空間、拖慢寫入。

</details>

### 題目 1（S1）：各門市每月已完成營業額（15 列跨月總覽）

- **題目與驗收**：身為營運經理，不用打開三個月的 Excel，一次列出 5 家門市在 2024 年 1、2、3 月各自「已完成」的訂單數與營業額。驗收應共 **15 列**，第一列為台中逢甲店 2024-01（`95`），15 列營業額加總必須等於第一季已完成金額 **`3,125`**。
- **✍️ 在 DBeaver 動手作提示**：用 `TO_CHAR(o.order_date, 'YYYY-MM')` 切出月份，串接 `orders`、`stores`、`order_items` 並過濾 `WHERE o.status = '已完成'`，計算訂單數時記得寫 `COUNT(DISTINCT o.order_id)`！

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
SELECT
    s.name AS 門市名稱,
    TO_CHAR(o.order_date, 'YYYY-MM') AS 月份,
    COUNT(DISTINCT o.order_id) AS 訂單數,
    SUM(oi.quantity * oi.unit_price) AS 營業額
FROM orders o
JOIN stores s ON o.store_id = s.store_id
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = '已完成'
GROUP BY s.name, TO_CHAR(o.order_date, 'YYYY-MM')
ORDER BY s.name, 月份;
```

**寫法重點**：一張訂單可能有多筆明細（例如 `ORD00001` 有兩筆商品），`orders JOIN order_items` 後訂單編號會出現兩次，所以計算張數一定要用 `COUNT(DISTINCT o.order_id)`。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
SELECT
    p.name AS 商品名稱,
    p.category AS 商品分類,

    SUM(oi.quantity * oi.unit_price) AS 營業額
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
JOIN products p ON oi.product_id = p.product_id
```

### 題目 3（S3）：找出 1、2、3 月都有消費的忠誠會員（同名必須分開）

- **題目與驗收**：身為行銷，要找出 1 月、2 月、3 月都留下 `已完成` 消費紀錄的忠誠會員發放優惠券。注意「謝哲瑋」和「劉欣宜」各有同名不同人，絕對不可只用姓名合併！驗收應找出 **3 位**會員，名單中同時包含兩位不同電話的「謝哲瑋」。
- **✍️ 在 DBeaver 動手作提示**：從 `customers` `JOIN orders`（自動排除 `customer_id IS NULL` 的散客），依 `c.customer_id, c.name, c.phone` 分組，用 `HAVING COUNT(DISTINCT TO_CHAR(o.order_date, 'YYYY-MM')) = 3` 篩出三個月都有買的人。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
SELECT
    c.customer_id,
    c.name AS 會員姓名,
    c.phone AS 會員電話,
    COUNT(DISTINCT TO_CHAR(o.order_date, 'YYYY-MM')) AS 消費月數,
    SUM(oi.quantity * oi.unit_price) AS 消費總額
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = '已完成'
  AND o.order_date BETWEEN '2024-01-01' AND '2024-03-31'
GROUP BY c.customer_id, c.name, c.phone
HAVING COUNT(DISTINCT TO_CHAR(o.order_date, 'YYYY-MM')) = 3
ORDER BY 消費總額 DESC, c.customer_id;
```

**寫法重點**：一定要把 `c.customer_id`（主鍵）放入 `GROUP BY`，兩位「謝哲瑋」（`0963-728-214` 與 `0943-645-351`）才不會被混在一起；而電話為 `0936-805-870` 的劉欣宜因為只在 1、3 月消費（缺 2 月），會被 `= 3` 精準剔除！

**實測輸出（共 3 列）：**

| customer_id | 會員姓名 | 會員電話 | 消費月數 | 消費總額 |
|---:|---|---|---:|---:|
| 7 | 謝哲瑋 | 0963-728-214 | 3 | 955 |
| 2 | 劉欣宜 | 0915-692-794 | 3 | 760 |
| 6 | 謝哲瑋 | 0943-645-351 | 3 | 425 |

</details>

### 題目 4（S4）：業績高於全體店員平均的績優店員名單

- **題目與驗收**：身為營運經理，想獎勵第一季已完成業績高於全體店員平均（`$313`）的店員，依業績高到低排序。驗收應列出 **4 位店員**：`曾思妤`（$950）、`張志明`（$680）、`李冠宇`（$440）、`蔡哲瑋`（$325）。
- **✍️ 在 DBeaver 動手作提示**：`WHERE` 裡不能直接寫彙總函式 `AVG(...)`！先用 CTE（`WITH staff_sales AS (...)`）算出每位店員的總業績，再於主查詢的 `WHERE 個人業績 > (SELECT AVG(個人業績) FROM staff_sales)` 比較。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
WITH staff_sales AS (
    SELECT
        st.staff_id,
        st.name AS 店員姓名,
        s.name AS 所屬門市,
        SUM(oi.quantity * oi.unit_price) AS 個人業績
    FROM staff st
    JOIN stores s ON st.store_id = s.store_id
    JOIN orders o ON st.staff_id = o.staff_id
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status = '已完成'
    GROUP BY st.staff_id, st.name, s.name
)
SELECT
    店員姓名,
    所屬門市,
    個人業績,
    ROUND((SELECT AVG(個人業績) FROM staff_sales), 0) AS 全體平均業績
FROM staff_sales
WHERE 個人業績 > (SELECT AVG(個人業績) FROM staff_sales)
ORDER BY 個人業績 DESC;
```

**寫法重點**：用 `WITH staff_sales AS (...)` 暫存每個店員的第一季成績單，後面不管是要比較大於平均值還是在欄位直接顯示全體平均（3,125 / 10 = 312.5 ≈ 313），都能輕鬆重複引用而不用寫兩段一樣的 4 表 JOIN。

**實測輸出（共 4 列）：**

| 店員姓名 | 所屬門市 | 個人業績 | 全體平均業績 |
|---|---|---:|---:|
| 曾思妤 | 高雄巨蛋店 | 950 | 313 |
| 張志明 | 台北信義店 | 680 | 313 |
| 李冠宇 | 台北車站店 | 440 | 313 |
| 蔡哲瑋 | 新竹巨城店 | 325 | 313 |

</details>

### 題目 6（E1）：各門市 1～4 月橫向營收樞紐表（`FILTER` 條件彙總）

- **題目與驗收**：主管想在簡報看「門市 × 月份」橫向展開的營收報表（欄位：`門市名稱`、`1月`、`2月`、`3月`、`4月`、`1至4月合計`），**即使某門市某月沒有已完成營收（如台北車站店 4 月僅一筆已退款單 `ORD00495`），也要顯示 `0`**！驗收總計五家加總須為 **`3,755`**。
- **✍️ 在 DBeaver 動手作提示**：從 `stores` 當左表 `LEFT JOIN orders ON s.store_id = o.store_id AND o.status = '已完成'`，再用 `COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE TO_CHAR(o.order_date, 'YYYY-MM') = '2024-04'), 0)` 橫向展開各月。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
SELECT
    s.name AS 門市名稱,
    COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE TO_CHAR(o.order_date, 'YYYY-MM') = '2024-01'), 0) AS "1月",
    COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE TO_CHAR(o.order_date, 'YYYY-MM') = '2024-02'), 0) AS "2月",
    COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE TO_CHAR(o.order_date, 'YYYY-MM') = '2024-03'), 0) AS "3月",
    COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE TO_CHAR(o.order_date, 'YYYY-MM') = '2024-04'), 0) AS "4月",
    COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS "1至4月合計"
FROM stores s
LEFT JOIN orders o
    ON s.store_id = o.store_id
   AND o.status = '已完成'
LEFT JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY s.store_id, s.name
ORDER BY "1至4月合計" DESC;
```

**寫法重點**：把直式的月份資料轉成橫式報表時，PostgreSQL 獨有的 `SUM(...) FILTER (WHERE ...)` 語法比傳統 `CASE WHEN` 更簡潔直覺，搭配 `COALESCE(..., 0)` 就能自動把台北車站店 4 月的空值轉為 `0`。

**實測輸出（共 5 列，總和 = 3,755）：**

| 門市名稱 | 1月 | 2月 | 3月 | 4月 | 1至4月合計 |
|---|---:|---:|---:|---:|---:|
| 高雄巨蛋店 | 50 | 345 | 605 | 125 | 1,125 |
| 台北信義店 | 330 | 115 | 360 | 255 | 1,060 |
| 新竹巨城店 | 110 | 325 | 60 | 190 | 685 |
| 台北車站店 | 380 | 60 | 130 | 0 | 570 |

</details>

### 題目 7（E2）：每月退單損失監控（`COUNT(DISTINCT order_id)` 防重複計數）

- **題目與驗收**：財務想追蹤 1～4 月每個月「`已退款` 或 `已取消`」的訂單張數與損失金額。注意像 `ORD000142` 或 `ORD00333` 單張單有兩項商品，絕對不能把退單張數錯算成 2 張！驗收 **4 個月各 1 張**，金額依序為 `120`、`250`、`245`、`115`。
- **✍️ 在 DBeaver 動手作提示**：條件寫 `WHERE o.status IN ('已退款', '已取消')`，張數一定用 `COUNT(DISTINCT o.order_id)`。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
SELECT
    TO_CHAR(o.order_date, 'YYYY-MM') AS 月份,
    COUNT(DISTINCT o.order_id) AS 退單張數,
    SUM(oi.quantity * oi.unit_price) AS 退單總金額
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status IN ('已退款', '已取消')
GROUP BY TO_CHAR(o.order_date, 'YYYY-MM')
ORDER BY 月份;
```

**寫法重點**：若誤寫成 `COUNT(*)`，`2024-02` 的 `ORD00142`（2 項商品）和 `2024-03` 的 `ORD00333`（2 項商品）會被膨脹成各 `2` 張退單；用 `COUNT(DISTINCT o.order_id)` 才會準確算出每月各 1 張。

**實測輸出（共 4 列）：**

| 月份 | 退單張數 | 退單總金額 |
|---|---:|---:|
| 2024-01 | 1 | 120 |
| 2024-02 | 1 | 250 |
| 2024-03 | 1 | 245 |
| 2024-04 | 1 | 115 |

</details>

### 題目 8（E3）：會員 vs 散客營收貢獻與平均客單價分析

- **題目與驗收**：行銷想知道 1～4 月「會員消費（`customer_id IS NOT NULL`）」與「散客消費（`customer_id IS NULL`）」在已完成訂單中的訂單數、總金額、平均客單價與營收佔比 `%`。驗收應得：會員 18 張（`$3,235`、客單 `$179.7`、佔比 `86.2%`）；散客 5 張（`$520`、客單 `$104.0`、佔比 `13.8%`）。
- **✍️ 在 DBeaver 動手作提示**：如果直接對明細 `AVG(quantity * unit_price)` 算的是「每杯平均單價」而不是「**每張訂單客單價**」！請先用 CTE 算好每張訂單的總金額與客群歸類，外層再 `AVG(訂單金額)` 與 `SUM(...) OVER ()` 算佔比。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
WITH order_totals AS (
    SELECT
        o.order_id,
        CASE WHEN o.customer_id IS NULL THEN '散客' ELSE '會員' END AS 客群類型,
        SUM(oi.quantity * oi.unit_price) AS 訂單金額
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status = '已完成'
    GROUP BY o.order_id, CASE WHEN o.customer_id IS NULL THEN '散客' ELSE '會員' END
)
SELECT
    客群類型,
    COUNT(*) AS 訂單張數,
    SUM(訂單金額) AS 總金額,
    ROUND(AVG(訂單金額), 1) AS 平均客單價,
    ROUND(SUM(訂單金額) * 100.0 / SUM(SUM(訂單金額)) OVER (), 1) AS 營收佔比百分比
FROM order_totals
GROUP BY 客群類型
ORDER BY 總金額 DESC;
```

**寫法重點**：兩階段彙總（先以 `order_id` 加總出每張單金額，再以客群類型取 `AVG`）是電商／餐飲計算客單價 (AOV) 的黃金模式；且兩組總金額加總 `3,235 + 520 = 3,755` 與題目 6 完全一致！

**實測輸出（共 2 列）：**

| 客群類型 | 訂單張數 | 總金額 | 平均客單價 | 營收佔比百分比 |
|---|---:|---:|---:|---:|
| 會員 | 18 | 3,235 | 179.7 | 86.2 |
| 散客 | 5 | 520 | 104.0 | 13.8 |

</details>

### 題目 9（E4）：各付款方式營收表現與客單價比較

- **題目與驗收**：財務想知道顧客偏好的付款工具：列出 1～4 月已完成訂單四種付款方式（`信用卡`、`LINE Pay`、`街口支付`、`現金`）的訂單張數、營收總額、平均客單價與營收佔比 `%`。驗收第一名須為 `信用卡`（8 張、`$1,495`、佔比 `39.8%`），`LINE Pay` 客單價最高（`$211.0`）。
- **✍️ 在 DBeaver 動手作提示**：沿用題目 8 的兩段式 CTE 思維，先把每張單的金額算出來，再依 `payment_method` 分組計算 `COUNT(*)`、`SUM`、`AVG` 與視窗函式佔比。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
WITH order_totals AS (
    SELECT
        o.order_id,
        o.payment_method AS 付款方式,
        SUM(oi.quantity * oi.unit_price) AS 訂單金額
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status = '已完成'
    GROUP BY o.order_id, o.payment_method
)
SELECT
    付款方式,
    COUNT(*) AS 訂單張數,
    SUM(訂單金額) AS 營收總額,
    ROUND(AVG(訂單金額), 1) AS 平均客單價,
    ROUND(SUM(訂單金額) * 100.0 / SUM(SUM(訂單金額)) OVER (), 1) AS 營收佔比百分比
FROM order_totals
GROUP BY 付款方式
ORDER BY 營收總額 DESC;
```

**實測輸出（共 4 列，營收總和 = 3,755）：**

| 付款方式 | 訂單張數 | 營收總額 | 平均客單價 | 營收佔比百分比 |
|---|---:|---:|---:|---:|
| 信用卡 | 8 | 1,495 | 186.9 | 39.8 |
| LINE Pay | 5 | 1,055 | 211.0 | 28.1 |
| 街口支付 | 5 | 630 | 126.0 | 16.8 |
| 現金 | 5 | 575 | 115.0 | 15.3 |

</details>

### 題目 10（E5）：Transaction 交易演練沙盒 — 模擬 4 月訂單 `ORD00491` 顧客退款並預覽影響（後用 `ROLLBACK` 還原）

- **題目與驗收**：模擬門市主管想在送出正式退款前試算影響：在 `BEGIN ... ROLLBACK;` 交易沙盒內把 4 月台北信義店的最大單 `ORD00491`（$255）狀態從 `'已完成'` 改為 `'已退款'`，立刻觀察 4 月各門市已完成營業額與已退款金額變化（台北信義店 4 月已完成從 `255` 掉成 `0`、已退款變成 `255`），看過數字後執行 `ROLLBACK;` 讓 `ORD00491` 恢復為 `'已完成'`！
- **✍️ 在 DBeaver 動手作提示**：先用 `BEGIN;`，接著用 `UPDATE orders SET status = '已退款' WHERE order_id = 'ORD00491' AND status = '已完成';`，立刻在同一個交易裡用 `SELECT ... FILTER (...)` 看報表前後差別，最後務必執行 `ROLLBACK;`。

<details>
<summary>參考解答與 PostgreSQL 實測結果</summary>

```sql
BEGIN;

-- 1. 模擬將台北信義店 4 月訂單 ORD00491 ($255) 改為已退款
UPDATE orders
SET status = '已退款'
WHERE order_id = 'ORD00491' AND status = '已完成';

-- 2. 交易內立即檢視 4 月各門市已完成與已退款金額變化
SELECT
    s.name AS 門市名稱,
    COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE o.status = '已完成'), 0) AS 交易內4月已完成營業額,
    COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE o.status = '已退款'), 0) AS 交易內4月已退款金額
FROM orders o
JOIN stores s ON o.store_id = s.store_id
JOIN order_items oi ON o.order_id = oi.order_id
WHERE TO_CHAR(o.order_date, 'YYYY-MM') = '2024-04'
GROUP BY s.name
ORDER BY s.name;

ROLLBACK;

-- 3. 驗證 ROLLBACK 成功：ORD00491 恢復為「已完成」
SELECT order_id, status FROM orders WHERE order_id = 'ORD00491';
```

| 門市名稱 | 交易內4月已完成營業額 | 交易內4月已退款金額 |
|---|---:|---:|
| 台中逢甲店 | 60 | 0 |
| 台北信義店 | 0 | 255 |
| 台北車站店 | 0 | 115 |
| 新竹巨城店 | 190 | 0 |
| 高雄巨蛋店 | 125 | 0 |

**實測輸出 — `ROLLBACK` 後確認：** `ORD00491` 的 `status` 維持為 `'已完成'`，台北信義店 4 月已完成營業額維持 `$255`（1～4 月合計維持 `$3,755`）。

</details>

## ⚠️ 常見卡關

| 狀況 | 原因 | 怎麼解 |
|---|---|---|
| 訂單數算出來跟商品列數一樣多 | `JOIN order_items` 造成一張訂單多列，卻寫了 `COUNT(*)` | 訂單張數一律改用 `COUNT(DISTINCT o.order_id)` |
| 兩位謝哲瑋在題目 3 合併成一列 | `GROUP BY c.name` 忘了放主鍵或手機 | `GROUP BY` 一定要包含 `c.customer_id, c.name, c.phone` |
| 題目 5 重跑交易檔時發現 `raw_sales` 變成 14 筆 | 交易最上面沒有先 `TRUNCATE raw_sales;` | 每次重跑月結交易檔開頭都先清空暫存表 `raw_sales` |
| 題目 8 平均客單價只有一百出頭左右 | 沒先用 CTE 依 `order_id` 加總訂單金額，直接平均單筆商品價格 | 先在 CTE 以 `order_id` 算出 `SUM(quantity * unit_price)` 再在外層 `AVG` |

## ✍️ 動手練

**1. 觀察題目 8（會員 86.2% vs 散客 13.8%）與題目 9（信用卡 39.8% vs LINE Pay 28.1%），為什麼兩張報表的總金額加起來都剛好等於 `3,755`？這代表什麼好習慣？**

<details>
<summary>看答案</summary>

這叫**跨報表交叉對帳 (Cross-Reconciliation)**！只要母體篩選條件相同（1～4 月 `status = '已完成'`），不論用門市分（題目 6）、客群分（題目 8）還是付款方式分（題目 9），總金額永遠都會收斂在 `3,755`；一旦某張報表漏了 `LEFT JOIN` 或沒寫 `DISTINCT` 導致數字跑掉，馬上就能抓出邏輯錯誤。

</details>

**2. 在題目 5 把 `4月新銷售明細` 加進資料庫後，如果你回頭重新跑一次題目 4（S4 業績高於平均的店員），哪幾位店員的個人業績或全體平均會改變？**

<details>
<summary>看答案</summary>

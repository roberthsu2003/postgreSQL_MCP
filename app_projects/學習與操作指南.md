# 實戰專案共用操作指南

八個專案都沿用同一套流程：先看懂一列 Excel 代表什麼，自己建表，再產生交易、核對資料，最後回答業務問題。第一次做建議從耗材開始；多表與門市月報留到 JOIN、分組、子查詢學完後。

## 每一步做到什麼才往下走？

| 步驟 | 你要做的事 | 過關條件 |
|---|---|---|
| 1 讀資料 | 下載 Excel，開啟「需求」與資料工作表，先手算一筆 | 能說出「一列」代表一項耗材、一筆打卡，或一項訂單商品 |
| 2 建結構 | 儲存自己的 `我的建表.sql`，依規格建表；壞資料逐筆測試 | 每筆錯誤符合指定限制，最後清空測試資料、保留表結構 |
| 3 寫資料 | 附上 Excel 與自己的 DDL，請 AI 產生 `建立資料.sql` | 成功提交交易，筆數、金額與下載表一致 |
| 4 寫查詢 | 依題目 1 → 10 的順序做；每題先手算／預測，再寫查詢 | 能解釋結果；MCP 查到的已提交資料與 DBeaver 相同 |
| 5～8 做 App | 先還原初始資料，再寫 PRD、待辦與程式 | 依專案的 `todolist.md` 逐項操作驗收 |

**Excel 沒辦法直接附給 AI 時**：複製指定工作表的「標題＋資料列」貼成表格，不要只貼截圖、需求故事或壞資料。請 AI 先回報看到的欄名、資料筆數和兩筆樣本，確認沒讀錯才產生交易。

## 在 DBeaver 怎麼執行？

先用以下查詢核對目前位置，再執行專案 SQL：

```sql
SELECT current_database() AS 目前資料庫, current_schema() AS 目前綱要;
```

- 建立資料庫的 `CREATE DATABASE` 要單獨執行，不能包進 `BEGIN`。建好後重新整理、連到新資料庫，再開 SQL 編輯器。
- 一般單句與壞資料測試：使用「執行 SQL 語句」，一次選取一個完整語句。
- 正常的 `BEGIN … COMMIT` 交易檔：使用 **SQL Editor → Execute SQL Script**，執行整份，確認最後成功提交。
- 故意報錯的實驗：先逐句執行到預期錯誤，接著執行 `ROLLBACK;`。不要依賴編輯器遇到錯誤後仍自動跑到最後。

建議本章先用自動提交模式（Auto-commit），只有講義明寫 `BEGIN` 時才開始多步驟交易。若使用手動提交模式，要確認測試種子資料已提交；否則一次 `ROLLBACK` 可能連先前的種子資料一起撤銷。

如果採用「同一資料庫內的獨立 schema」替代方案，每次開新 SQL 編輯器都要先設定該專案的 `search_path`。MCP 是另一個連線，**不會繼承 DBeaver 的設定**；提示詞要改成實際資料庫名稱與 schema 名稱，查詢加上 `schema.表名`，結構檢查也別再限定 `public`。

## 交易內的結果，要在哪裡看？

| 時機 | 在原 DBeaver 連線查詢 | 在 MCP 另一個連線查詢 |
|---|---|---|
| 已 `BEGIN`、尚未提交 | 看得到自己的修改，可預覽沙盒結果 | 看不到這筆尚未提交的修改 |
| 已 `COMMIT` | 看得到新資料 | 可驗證提交後資料 |
| 已 `ROLLBACK` | 回到修改前 | 可驗證資料已還原 |

因此「沙盒內金額」要在同一個 DBeaver 編輯器裡查；MCP 用來核對提交或還原後的結果。交易中的限制錯誤會讓後續語句失敗，先 `ROLLBACK` 再繼續。[PostgreSQL 交易與隔離說明](https://www.postgresql.org/docs/current/transaction-iso.html)

`SERIAL` 是取號機：即使寫入失敗或 `ROLLBACK`，取過的號碼也可能不回收。看到跳號時先核對人物／商品的識別資料，不要為了連號任意修改主鍵。

## 範例看不懂時，先把長查詢拆成三步

以報銷為例：先從 `claims` 查出「待撥款的單號與金額」；再 JOIN `employees` 加上姓名；最後 JOIN `departments`、`categories` 補上部門與類別。每多接一張表，就先看筆數是否合理。

`INSERT ... SELECT` 若查不到對應的商品或會員，可能成功執行卻寫入 0 筆；交易不會把 0 筆當成錯誤。請核對 `RETURNING`／受影響筆數，以及預期的訂單與明細數，才能發現「有單頭、沒明細」的情況。

先回答「我要篩哪些列」，再回答「要補哪些表的欄位」，最後才做「加總、分組、排序」。`FILTER` 是只對符合條件的列加總，`COALESCE(..., 0)` 是把沒有資料時的空值顯示為 0，`WITH` 則是把中間查詢命名，方便下一段使用。

遇到 E 題的新語法，先回目錄的先修連結，再以一兩筆資料觀察中間結果。寫得出最後答案之外，也要能說明為什麼 `LEFT JOIN` 要保留空白列、為什麼訂單數要去除重複。

## 做完 DML，進入 App 前先還原

步驟 4 會真的扣庫存、加設備、改部門、核准或結案。**順利做完也要還原**，因為範例 PRD 與 App 待辦使用步驟 3 的初始基準。

只在該專案的練習資料庫執行對應那一列；一次清空有相依關係的全部資料表，保留結構，再重跑自己儲存的 `建立資料.sql`。門市專案重跑的是第一季交易，先不要重跑 4 月交易。

| 專案 | 清空資料的 SQL（請選自己的專案，別全部執行） |
|---|---|
| 1 | `TRUNCATE TABLE supplies;` |
| 2 | `TRUNCATE TABLE devices;` |
| 3 | `TRUNCATE TABLE attendance, employees;` |
| 4 | `TRUNCATE TABLE claims, employees, categories, departments RESTART IDENTITY;` |
| 5 | `TRUNCATE TABLE order_items, orders, products, customers RESTART IDENTITY;` |
| 6 | `TRUNCATE TABLE tickets, categories, agents RESTART IDENTITY;` |
| 7 | `TRUNCATE TABLE guest_enrollments, employee_enrollments, guests, employees, courses RESTART IDENTITY;` |
| 8 | `TRUNCATE TABLE order_items, orders, customers, products, staff, stores, raw_sales RESTART IDENTITY;` |

若交易還開著，先結束交易再清空。手動提交模式下，清空後還要提交，才重新執行資料交易檔。還原完成後重跑步驟 3 的對帳查詢，通過才進入步驟 5。

如果只是要繼續做 E 題，不要中途還原：E 題多半接續 S 題的操作狀態。若已還原，就按順序重做會修改資料的 S 題。

## 卡住時提供什麼？

把「專案與步驟、`current_database()`／`current_schema()`、完整 SQL、第一個 ERROR、預期與實際結果」一起交給 AI。不要只貼最後一條 `current transaction is aborted`，真正原因通常在更前面的第一個錯誤。

MCP 暫時連不上時，可以先完成 DBeaver 的手寫與核對；等連線恢復再補交叉驗證。工具呼叫名稱與切換資料庫能力以你安裝版本為準，先請 AI 列出可用工具及實際連線目標，再查詢。[Microsoft Postgres MCP 官方使用說明](https://github.com/microsoft/postgres-mcp/blob/main/USAGE.md)
